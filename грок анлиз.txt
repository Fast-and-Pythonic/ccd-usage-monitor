Ниже — инженерный разбор по фактам. Где цифр нет на Windows 10 @125% для окна ~500×34 — так и написано. Ваши 121 / 277 / 310 МБ принимаю как единственный сопоставимый замер именно этой формы окна.

## Короткий ответ на главный вопрос

**Нет, CSS не оправдывает ~190 дополнительных мегабайт для пилюли, которая живёт в RAM сутками.** WebView2 — это не «рендер HTML», это отдельный набор процессов (ваш замер: 7 процессов, 277–310 МБ даже на пустой странице). Этот пол не уедет в release.

Уровень 3 (произвольная вёрстка) достигается **декларативным файлом темы**, не обязательно CSS. Slint-interpreter грузит полную разметку в рантайме и остаётся в том же порядке величин, что и текущий egui, а не в зоне WebView.

Рекомендация в конце — одна.

# Кандидаты

## 1. Tauri 2 (WebView2)

### Память
**Проверено вами:** Tauri 2.11, пустая страница — 7 процессов, **310 МБ** resident; wry+tao — **277 МБ**. Rust-процесс 20–27 МБ, остальное — WebView2. Это нижняя граница.

Сторонние сопоставимые цифры (другая ОС/другое окно, не переносить 1:1): на macOS в сравнительном прогоне gallery/editor Tauri держался в районе **250–330 МБ** после GC.

### Рантайм-кастомизация
Грузится **и стиль, и разметка** (HTML+CSS+JS) с диска / из строки. Перезапуск приложения не нужен: достаточно перечитать файлы и подменить DOM/`adoptedStyleSheets`. Язык темы — CSS (+HTML). Это единственный кандидат, где автор темы пишет буквально как для Waybar.

### Прозрачность / always-on-top / click-through (Windows)
- Прозрачность и `decorations: false` — штатно в конфиге; у вас на Tauri уже работает.
- Тень: `shadow: false` / `set_shadow(false)`. На Win10 у undecorated+shadow=true бывает **1 px белая кайма**; на Win11 — скругление системой. Документация Tauri это фиксирует.
- Always-on-top — штатный флаг.
- Click-through — штатный API `set_ignore_cursor_events(true)` → в tao это `WS_EX_TRANSPARENT | WS_EX_LAYERED`. Переключается в рантайме.

Известные дыры:
- **Попиксельный** click-through (клик проходит только по прозрачным пикселям, непрозрачные ловят) в WebView2 на Windows **не решён**. У Wails это расписано как взаимоисключение «видно насквозь» vs «клики насквозь»: `IgnoreMouseEvents` даёт click-through, но ломает per-pixel alpha через `SetLayeredWindowAttributes(..., LWA_ALPHA)`. `WS_EX_TRANSPARENT` на host HWND недостаточно, потому что клики ест child `Chrome_WidgetWin_*`.
- Та же потребность открыта как feature request в Tauri (#13070).
- Регрессии прозрачности WebView2 (артефакты/ложный titlebar на runtime 144+) — отдельные баги runtime, не Tauri.

Для вашей модели («весь режим click-through / весь обычный», вход через трей) штатного `set_ignore_cursor_events` **достаточно**. Per-pixel вам не обязателен.

### Пиксельная точность @125%
**Гарантии нет.** В CSS `1px` = 1 CSS-пиксель = 1 логический. При 125% DPR = 1.25, линия `height: 1px` занимает 1.25 физических пикселя и растрится с AA. Физический 1 px получают через `1 / devicePixelRatio` (= 0.8 CSS px) плюс надежда, что compositor попадёт в пиксельную сетку. Chromium это часто делает приемлемо, но **контракт «ровно 1 физический пиксель, цифры не прыгают» Web-стеком не даётся.** Фиксированную ширину ячеек в логических px выдержать можно; «не дёргаться» на дробном DPI — уже ручная сетка и `image-rendering`, не гарантия.

### Барьер темы
Минимальный из всего списка. CSS знают все целевые авторы.

### Поставка
Бинарник Tauri сам небольшой. На Win11 WebView2 уже есть; на Win10 Evergreen обычно тоже раскатан Microsoft, но это **внешний runtime**. Offline/Fixed Version — **+127…180+ МБ** к установщику.

### Связь с Rust
Штатные IPC-команды. Для индикатора квот — нормально. Для 60 Hz перерисовки полосок — лишний хоп; на практике для редко меняющихся цифр терпимо.

## 2. Slint + slint-interpreter

### Память
**Замера окна 500×34 @ Win10 125% нет** (ни у вас, ни в публичных бенчах под эту геометрию).

Что есть, с пометкой контекста:
- Maintainer Slint (не ваш стенд): пустое окно ~1200×800 — **slint-viewer + Skia ≈ 20 МБ**, тот же бэкенд Qt ≈ 18 МБ, `qmlscene` ≈ 35 МБ. Бинарь шаблона Windows ≈ **2.6–3.6 МБ** (femtovg, LTO+strip).
- Пользовательский отчёт Windows, winit+skia, несколько окон: база **~50 МБ**, при нехватке RAM процесс сам сжимался до **~3 МБ**.
- Регрессия на Windows 11, winit/skia, маленький плеер: **1.13.1 ≈ 10 МБ → 1.14.1 > 100 МБ → 1.15.1 ≈ 50 МБ**. Версию надо пинить и мерить самим.
- Анекдот Linux (не Windows): смена egui→Slint software renderer у системного монитора **~135 → ~30 МБ** за счёт отказа от GPU-стека. Для всегда-висящей 2D-пилюли software/femtovg — разумная гипотеза, не факт.

Ожидание (гипотеза, не замер): **сопоставимо с вашим egui (~порядок 50–120 МБ), не 300 МБ.** Подтверждать только своим релизом на том же стенде.

Интерпретатор тянет компилятор `.slint` в процесс. Насколько именно — **не измерено**. slint-viewer это делает и остаётся в цифрах выше.

### Рантайм-кастомизация
Грузится **полная декларативная разметка + стили** из `.slint` или из строки: `Compiler::build_from_path` / `build_from_source`, затем `ComponentDefinition::create()`. Есть live-reload (`LiveReloadingComponent`, `slint-viewer --auto-reload`). Перезапуск приложения не обязателен; пересоздаётся дерево компонентов. Контракт с ядром — именованные `in`-свойства и callbacks.

Язык темы — **Slint**, не CSS. Градиенты, анимации, `for` по модели, абсолютные координаты, другая форма окна — это уровень 3, не «только цвета».

Ограничение (проверено словами мейнтейнера): **встроенный widget style** (fluent/material/qt) компилируется вместе с UI и **на лету не меняется**. Для кастомной пилюли это почти неважно: вы не используете стандартные виджеты как основу темы.

Лицензия: desktop можно держать проприетарным под Royalty-free (нужна атрибуция Slint) либо GPL-3, либо коммерция. Для десктопа это не блокер.

### Прозрачность / always-on-top / click-through
Документированные свойства `Window`: `no-frame`, `always-on-top`, `background: transparent`. Maintainer подтверждает связку transparent + no-frame. `always-on-top` работает на Windows и X11, **не на Wayland** (ограничение протокола, не баг Slint).

Click-through **первого класса нет**. В обсуждении #5111: «works fine with backend crates» / «нужен OS-specific пакет»; кроссплатформенной абстракции нет. На Windows это тот же `WS_EX_TRANSPARENT | WS_EX_LAYERED` через `raw-window-handle` у winit-окна. Объём работы — десятки строк, не архитектура. Тень DWM — тоже Win32 (`DWMWA_NCRENDERING_POLICY` / `DWMWA_WINDOW_CORNER_PREFERENCE`), Slint это не прячет.

Известные окна-баги: `no-frame` ломал нативный resize (для фиксированной пилюли нерелевантно); повторный `apply_window_properties` при анимации когда-то дёргал z-order.

### Пиксельная точность @125%
**Лучший контракт в шорт-листе.** В языке две единицы: `px` (логические) и **`phx` (физические)**. Линия `height: 1phx` — ровно один физический пиксель по спецификации. Масштаб берётся с окна; override — `SLINT_SCALE_FACTOR`.

Оговорка: это гарантия модели координат, не лабораторный скриншот вашей полоски на 125%. AA текста/градиентов всё равно будет. Для 1 px индикатора `phx` — правильный примитив; в CSS такого примитива нет.

### Барьер темы
Выше CSS. Синтаксис близок к QML: свойства, биндинги, анимации. Документация хорошая, LSP/превью есть. Для «разработчик + агент» — приемлемо; для «скопировал CSS с Codepen» — нет. Это главная цена отказа от WebView.

Нужен **стабильный манифест темы**: обязательные `in`-свойства (`quota-used`, `context-fill`, список модулей) и запрет трогать оконные флаги, которые ломают always-on-top.

### Поставка
Один процесс, статическая линковка. Внешнего runtime нет. Размер дистрибутива: единицы МБ + ваши ресурсы. Skia-рендерер раздувает бинарь (~20 МБ в одном отчёте vs ~3.5 МБ femtovg).

### Связь с Rust
Ноль мостов. Интерпретатор и ядро в одном адресном пространстве. Свойства выставляются напрямую.

## 3. Qt / QML

### Память
**Замера 500×34 @ Win10 125% нет.**

Есть: тот же комментарий мейнтейнера Slint — пустой `qmlscene` ≈ **35 МБ** на ~1200×800. Это не ваше окно и не ваш Qt 6.x, но порядок «десятки МБ, не сотни» подтверждён. Бинарь+DLL Qt Quick на Windows стартует с **~13–14 МБ** на диске (Core+Gui), реальный windeployqt для QML — больше из-за плагинов и QML-модулей.

Резидентная память живого QML с GPU-RHI на Windows часто выше 35 МБ; публичного замера «одна полоска 500×34» нет.

### Рантайм-кастомизация
Грузится **полная QML-разметка** (`QQmlComponent` / `Loader.source` / `QQmlApplicationEngine::load`). Стили — свой QML + `qtquickcontrols2.conf` / кастомные типы. Смена `Loader.source` уничтожает старое дерево, перезапуск процесса не нужен. Язык темы — QML (не CSS; Qt Stylesheets — это виджеты, не Quick).

Уровень 3 — да: произвольная вёрстка, градиенты, анимации, другая форма.

### Прозрачность / always-on-top / click-through
Рабочая связка, многократно описанная:

```qml
Window {
    color: "transparent"
    flags: Qt.FramelessWindowHint | Qt.WindowStaysOnTopHint
}
```

Click-through — не QML-свойство, а `SetWindowLong(winId(), GWL_EXSTYLE, WS_EX_TRANSPARENT | WS_EX_LAYERED)`. HWND стабилен. Per-pixel hit-test в Qt тоже не бесплатный; для режима «всё окно насквозь» Win32 достаточно.

Тень DWM и кайма Win10 — типичные грабли frameless Qt; обходят QWindowKit / ручной `WM_NCCALCSIZE`. Это известная инженерия, не блокер.

### Пиксельная точность @125%
QML живёт в device-independent pixels. `1` ≠ 1 физический px при 125%. Есть `Screen.devicePixelRatio` и можно задать высоту `1 / Screen.devicePixelRatio`. Сцена-граф растеризует через RHI (D3D11 по умолчанию на Windows). **Гарантии «ровно 1 физический пиксель» в документации нет** — только ручной пересчёт. Высокий шанс попасть, если выравнивать координаты на физическую сетку; это нужно кодировать в теме или в хелпере.

### Барьер темы
QML знакомы части десктоп-разработчиков, CSS-авторам — средний. Агентам QML даётся хорошо. Экосистема примеров огромная.

### Поставка
windeployqt копирует набор DLL + `qml/` + плагины платформы. На машине пользователя нужен **MSVC Redistributable**. Лицензия: LGPL-3 (динамическая линковка + предоставление object files при модификации Qt) или коммерческая Qt. Для оверлея это юридический и паковальный налог, которого у Slint/egui нет.

### Связь с Rust
cxx-qt / qmetaobject-rs / отдельный C++ shim. Мост живой, но это второй язык в репозитории и отдельный CI. Стоимость выше, чем у Slint, ниже, чем у «написать свой layout engine».

## 4. GTK4 + CSS + GtkBuilder

### Память
**Замера 500×34 @ Win10 125% нет.** На Windows GTK4 historically плох: «abnormal» память hello-world на Win11 (#5085), утечки 4.12, утечки GSK ngl 4.16 на DrawingArea (потом чинили). Это не «GTK лёгкий на Linux, значит лёгкий на Windows».

На Linux GTK4 в чужих бенчах близок к Slint/Qt (сотни не те). На ваш целевой стенд это не переносится.

### Рантайм-кастомизация
- Стили: `CssProvider::load_from_path` / `load_from_string` в рантайме, без перезапуска. Это настоящий CSS (подмножество GTK).
- Разметка: `GtkBuilder` грузит `.ui` XML с диска. Смена набора модулей = пересборка виджетов из XML + CSS.
- Уровень 3 ограничен виджетами GTK: «другая форма пилюли» = кастомный `GtkDrawingArea` / CSS `border-radius`, не свободный scene graph как в QML/Slint. Произвольные градиенты/анимации — слабее Quick/Slint.

### Прозрачность / always-on-top / click-through
На Windows — GDK Win32 backend, официально существует. Стабильность прозрачного always-on-top оверлея **не задокументирована как first-class scenario**; публичных «делай так» для GTK4-Win оверлея мало.

Click-through: `gdk_surface_set_input_region` (дырка в input region). На Linux это проверенный приём; на Windows — предполагаемо работает через тот же GDK API, **подтверждённого репорта под Win10 нет**.

### Пиксельная точность @125%
GTK CSS `px` — не физический пиксель. Масштаб задаёт Win32 DPI awareness + `gtk-xft-dpi`. Линия в 1 физический px — ручной cairo/GSK, не CSS. **Гарантии нет.**

### Барьер темы
Для CSS-авторов лучший после Tauri. `.ui` XML — отдельный навык. Сообщество тем «как у Waybar» на GTK4-Windows почти отсутствует.

### Поставка
Самый тяжёлый Windows-story в списке: gvsbuild/MSYS2, пачка DLL (glib, cairo, pango, graphene, harfbuzz, rsvg…). Пользователю нужен ваш бандл GTK, не системный компонент. Это не WebView2, но и не «один exe».

### Связь с Rust
gtk4-rs зрелый. Мост — GObject, не IPC.

### Linux-будущее
Единственный кандидат с **готовым layer-shell**: gtk4-layer-shell. Поддерживается на wlroots (Sway/Hyprland), Smithay (COSMIC), по вашей же пометке — KDE; **не на GNOME/Mutter**. winit/tao/Slint/Tauri/Avalonia layer-shell не дают. Это реальный плюс GTK, но только если Linux-версия станет обязательной и целевые композиторы — не GNOME.

Как **основной** стек под Windows 10/11 — слабый выбор из-за качества порта и утечек.

## 5. Avalonia (XAML + AvaloniaXamlLoader)

### Память
**Замера 500×34 @ Win10 125% нет.**

Ориентиры:
- Self-contained hello-world на диске ≈ **80 МБ** (без trim/AOT).
- NativeAOT-шаблон: диск ~18 МБ, автор заявляет RAM ~20 МБ — **не ваш стенд, не ваше окно**.
- Форумные цифры пустого окна .NET 8: порядка **75 МБ** + иногда доп. процессы.
- Maintainer Avalonia считал **~250 МБ «не исключительно много»** для типичного .NET GUI — это культурный масштаб фреймворка.

Ожидание: не хуже Tauri по диску при self-contained, по RAM скорее **между egui и Tauri**, ближе к верхней половине. Без своего замера утверждать нельзя.

### Рантайм-кастомизация
`AvaloniaRuntimeXamlLoader` / `AvaloniaXamlLoader.Load` грузит **XAML с диска/из потока** — и стили (`StyleInclude`), и деревья контролов. Перезапуск не обязателен. Тема пишется на **XAML**, не CSS. Уровень 3 — да (контролы, градиенты, анимации, геометрия). Смена темы = заменить `Application.Current.Styles` + пересобрать content.

Издержки: runtime-парсер XAML тяжелее скомпилированного BAML-аналога; для пилюли размер дерева крошечный.

### Прозрачность / always-on-top / click-through
Прозрачность и `SystemDecorations="None"` / `Topmost` — штатно.

Официальная документация Avalonia: **«currently does not support WPF-like transparent click-through»**, делать через native interop. Это не «не работает», это «сами ставьте `WS_EX_TRANSPARENT`». Репорта об успехе достаточно (SO, обсуждения #15836, #17304). Per-pixel à la WPF `AllowsTransparency` — открытое ограничение, collaborator: «known limitation which no one had time to fix».

Для вашего бинарного режима click-through — решаемо так же, как в Slint.

### Пиксельная точность @125%
DIP-система как у WPF. `1` = логический пиксель. Физический 1 px: делить на `RenderScaling` (1.25). **Гарантии snap-to-pixel в документации нет.** У Avalonia лучше контроль над render scaling, чем у CSS, хуже явного `phx`.

### Барьер темы
XAML знают .NET-разработчики; CSS-авторам — новый язык. Агенты XAML пишут сносно. Хуже CSS и чуть хуже Slint/QML для вашей аудитории.

### Поставка
Либо self-contained (.NET внутри, десятки МБ), либо framework-dependent (нужен установленный .NET 8+). Внешнего «как WebView2» нет, но runtime тяжелее нативного Rust.

### Связь с Rust
Отдельный процесс или хостинг CLR. Для Rust-ядра это второй рантайм в памяти и IPC/FFI. Стоимость высокая относительно Slint.

# Linux / Wayland (проверка ваших тезисов)

**Подтверждается:**
- Обычный xdg-shell клиент **не задаёт** глобальную позицию и не требует always-on-top. Это политика композитора.
- **wlr-layer-shell** закрывает панель/оверлей на wlroots и (в вашей формулировке) KDE; gtk4-layer-shell это реализует. Ещё Smithay/COSMIC.
- **Mutter/GNOME layer-shell для сторонних приложений по-прежнему нет** как стабильного пути «повесь пилюлю здесь».
- winit и tao **не** реализуют layer-shell. Slint сидит на winit — значит, на GNOME Wayland у вас не будет ни позиции, ни always-on-top. Это уже сказано мейнтейнерами Slint.

Следствие: выбор GUI на Windows **не обязан** совпадать с Linux-панелью. Честная стратегия — Windows сейчас на Slint/winit; если Linux понадобится на GNOME, это отдельный backend (GTK4+layer-shell **или** X11-only **или** расширение композитора), а не аргумент ставить GTK4 на Windows сегодня.

# CSS vs свой рендерер: цена 190 МБ

Структура расхода у WebView-стека (ваш замер):

- ~20–27 МБ — Rust
- ~250–290 МБ — процессы WebView2
- 7 процессов вместо 1
- GPU/композитор Edge живёт, пока живёт пилюля

Пилюля 500×34 логических px при 125% — это ~625×43 физических. Держать ради неё полный браузерный runtime, чтобы авторы писали `background: linear-gradient(...)` вместо `background: @linear-gradient(...)` в `.slint`, — плохой обмен для resident-процесса «с утра до ночи».

Что даёт «самостоятельный рендерер» из шорт-листа:

- **Уровни 1–2** закрываются чем угодно декларативным (Slint, QML, XAML, даже JSON поверх egui).
- **Уровень 3** закрывается Slint и QML без CSS. Форма пилюли, порядок модулей, градиенты, анимации — да.
- **CSS как социальный протокол тем** — единственный уникальный актив Tauri. Он стоит ~190 МБ + 6 лишних процессов + дробный DPI без `phx` + чужие регрессии WebView2.

Для сообщества формата Waybar/Rainmeter важнее не буквально CSS, а **файл темы + hot reload + документация контракта**. Rainmeter не CSS. Polybar — ini. Waybar — CSS, потому что GTK. Прецедент не обязывает браузер.

# Рекомендация

**Брать Slint с `slint-interpreter` как слой тем. Ядро оставить на Rust. Tauri не брать. Qt — запасной, если Slint не пройдёт ваш же замер памяти или click-through на конкретной сборке Windows.**

Почему не список, а один выбор:

1. Главное требование — **рантайм-загрузка вёрстки**, не «ещё одна ветка в painter». Интерпретатор это делает. egui не делает. Flutter/Iced не делают.
2. Налог WebView вы уже измерили: **+190 МБ и 6 процессов**. Для resident-оверлея это проигрыш по определению продукта («висит сутками»).
3. Пиксельный контракт: только Slint даёт `1phx` в языке темы. Остальные предлагают делить на DPR вручную.
4. Мост с ядром — нулевой. Qt/Avalonia/GTK добавляют второй runtime или второй язык.
5. Windows-окно нужной формы собирается из документированных флагов Slint + 1 страница Win32 на click-through и снятие тени DWM. Это меньше риска, чем WebView2 child-HWND.
6. Поставку не завязываете на Evergreen WebView2 / .NET / gvsbuild.

Что сделать в первую очередь (не теория):

1. Release-сборка на **вашем** стенде Win10 125%: пустое `no-frame` окно 500×34, femtovg и skia отдельно, версии 1.13 vs актуальная (регрессия 1.14 реальна). Сравнить resident с 121 МБ egui.
2. Протокол темы: один `export component Pill` с фиксированными `in`-свойствами. Примеры тем — в репозитории, как у Waybar.
3. Click-through и DWM shadow — сразу через `raw-window-handle`, не ждать upstream.
4. Если interpreter раздует бинарь/RAM неприемлемо — компилировать дефолтную тему, а user-theme грузить интерпретатором только при наличии файла (два режима в одном бинаре).
5. Linux не решать этим коммитом. Если позже понадобится GNOME — отдельный GTK-backend, не причина менять Windows-стек.

Qt/QML выбирайте только если после замера Slint окажется ≥200 МБ или интерпретатор окажется непригоден (лицензия/атрибуция/баги no-frame). CSS-путь (Tauri) оставляйте как сознательный продуктовый обмен «сообщество тем любой ценой ↔ +190 МБ резидента», не как инженерный оптимум. Для описанного приложения этот обмен не сходится.
